# Roamio 问题清单

更新时间：2026-05-04

## 总体判断

Roamio 当前不是单点 bug 问题，而是长期快速迭代后形成的系统性维护问题。项目仍有明确产品价值和可复用代码，但安全、配置、结构、文档真实性、测试和部署链路都需要先整理。

## P0：立即处理

### 1. 敏感信息泄露风险

现象：
- 文档中仍可搜索到疑似真实 API Key、数据库地址、数据库密码、`SECRET_KEY`、`QQ_APP_KEY`。
- `roamio/settings.py` 中存在默认 `SECRET_KEY` 和默认 `QQ_APP_KEY`。
- 历史提交曾多次出现安全修复，说明仓库历史里可能仍保留过敏感信息。

风险：
- 如果仓库公开过，所有出现过的密钥都应按已泄露处理。
- JWT 共享密钥泄露会影响 Roamio 与 Ralendar 的认证互信。

初步处理：
- 轮换所有出现过的密钥和密码。
- 删除或脱敏文档中的真实信息。
- 增加提交前密钥扫描。

### 2. 生产/开发配置混用

现象：
- `DEBUG = True` 固定写在 `settings.py`。
- 数据库固定使用 MySQL backend，但仓库里仍有 `db.sqlite3`。
- Redis 缓存被强制启用，缺少本地降级策略。
- 开发、生产、第三方服务配置集中在一个 settings 文件。

风险：
- 本地启动门槛高。
- 生产安全状态不可控。
- 新环境部署容易失败。

初步处理：
- 拆分 `settings/base.py`、`settings/dev.py`、`settings/prod.py`。
- 通过环境变量决定数据库、缓存和调试模式。
- 提供可用的 `.env.example`。

### 3. 工作区存在重复项目目录

现象：
- 根目录存在未跟踪目录 `roamio-master/`，看起来是一份完整项目拷贝。

风险：
- 搜索、统计、审查容易读到重复代码。
- 后续误改或误提交概率高。

初步处理：
- 确认该目录来源。
- 如果只是备份/解压残留，移出仓库或删除。
- 如果有保留价值，先归档说明，不参与主线开发。

## P1：高优先级

### 4. 后端职责边界混乱

现象：
- 同时存在旧 `backend.views/backend.urls` 和新 `/api/v1/` DRF ViewSet。
- `SiteStat`、旧旅行页面、新 `Trip`、评论系统之间存在兼容逻辑。
- `backend` 单一 Django app 承载用户、旅行、评论、AI、Ralendar、支付、存储等多个领域。

风险：
- 修改入口不清晰。
- 新功能容易写到错误层。
- 兼容逻辑越来越难删除。

初步处理：
- 列出所有路由和实际前端调用。
- 明确旧接口冻结策略。
- 先按目录边界整理，再决定是否拆 Django app。

### 5. AI 模块稳定性不足

现象：
- 当前工作区对 `backend/utils/ai/ai_service.py` 有本地修改。
- 最新提交修复了 `trip_title` 缺失 fallback，但本地修改可能又把它改回强校验。
- AI JSON 解析、提示词长度、返回结构和前端保存链路耦合较强。

风险：
- AI 生成不稳定会直接影响核心编辑流程。
- 模型输出变化会导致保存失败。

初步处理：
- 先确认本地修改意图。
- 为 AI 输出清洗增加单元测试。
- 把模型调用、JSON 解析、业务映射拆开。

### 6. 文档与代码状态不一致

现象：
- 文档数量多，但混合了规划、总结、宣传、部署记录和真实技术规范。
- 部分文档提到不存在或位置已变化的文件。
- 文档中技术栈表述存在 Django 4.2/5.2、SQLite/MySQL 等混杂。

风险：
- 重新接手时容易被过期文档误导。

初步处理：
- 给文档分层：当前事实、历史记录、规划草案。
- 更新 README，使其只指向当前可信文档。

## P2：中优先级

### 7. 测试覆盖薄弱

现象：
- `backend/tests.py` 存在，但没有看到覆盖核心业务的系统化测试。
- 前端缺少可见测试体系。

风险：
- 大规模整改没有安全网。

初步处理：
- 先补后端 smoke tests：认证、Trip CRUD、AI 清洗、评论、公开/私有权限。
- 前端先补最小构建检查和关键页面手测清单。

### 8. 前端状态和请求层需要整理

现象：
- 使用自写 fetch/XHR 请求封装。
- token、401、错误响应、上传进度、公共页面跳转逻辑集中在同一请求层。
- 路由中包含临时跳转页 `/2025_review`。

风险：
- 请求错误处理和认证状态容易互相影响。

初步处理：
- 明确请求返回格式。
- 统一错误对象。
- 把临时活动页面与主应用路由隔离。

### 9. 构建产物提交策略需要确认

现象：
- `web/dist/` 构建产物提交到仓库。

风险：
- 每次前端改动会产生大量构建噪音。
- 但如果当前服务器依赖 `git pull` 直接发布 dist，贸然删除会破坏部署。

初步处理：
- 先确认部署链路。
- 若仍依赖 dist 提交，暂时保留。
- 后续引入构建部署流程后再调整。

## P3：后续优化

- 支付/订阅模块的实际使用状态待确认。
- Ralendar 集成需要区分已上线能力和规划能力。
- 地图、天气、COS、邮件等外部服务需要统一适配层。
- 代码编码显示在当前 PowerShell 中异常，需要确认文件编码和终端编码策略。
